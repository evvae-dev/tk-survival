# 삼국지 챕터 순차 개발

## 목표와 진행 원칙

사용자가 요청한 챕터를 **사건 원본 → 사건 데이터 → 실행 흐름 → 게임·관리자 연결 → QA·수정 → 이미지 생성·연결 → 최종 검증 → 챕터 완료** 순서로 개발한다. 한국어로 진행 상황을 알린다.

`1~3화 개발해줘`라면 **1화의 모든 완료 조건을 충족한 후 2화, 그다음 3화**를 진행한다. 다음 화의 범위·연결점을 미리 읽을 수 있지만, 현재 화가 미완료인 채 다음 화의 데이터·분기·이미지를 구현하지 않는다. 번호가 연속이라는 이유로 게임 내 모든 사건을 강제로 직렬 연결하지 않는다.

스킬 작성 요청은 스킬 파일만 작성한다. 실제 챕터 개발은 개발 요청을 받았을 때 시작한다. 지정 범위의 개발 요청은 그 범위의 데이터 작성·분기 구현·로컬 검증·필요한 분기 이미지 생성을 포함한다. 이미 승인된 범위와 단계별 재진행을 다시 묻지 않는다. 외부 공유 게시·운영 배포는 별도의 실제 요청 범위를 따른다.

## 사용하는 스킬과 규칙

처음 사용할 때 사용 중인 스킬을 사용자에게 짧게 알리고 다음 파일을 실제로 읽는다. 링크가 없으면 저장소 내 이름으로 검색한다. 필수 스킬이 끝내 없으면 그 단계는 차단 상태로 기록하고 이유를 알린다.

- 실행 흐름: [three-kingdoms-flow](../three-kingdoms-flow/SKILL.md). 설계 모드로 사용하고 [분기 템플릿](../three-kingdoms-flow/references/flow-template.md)을 따른다.
- 검수: [three-kingdoms-qa](../three-kingdoms-qa/SKILL.md). 문구·설계 평가와 실제 실행 QA를 모두 수행한다. [경로 매트릭스](../three-kingdoms-qa/references/qa-matrix.md)를 대상 챕터에 맞게 채운다.
- 화면 검증: [.agents/skills/playwright-page-check/SKILL.md](../playwright-page-check/SKILL.md). 실제 게임·관리자·PC/모바일 검증에 사용한다.
- 프로젝트 `AGENTS.md`, `docs/EVENT_COLLECTION_RULES.md`, `docs/EVENT_WRITING_GUIDE.md`, `docs/ABILITY_CHECKS.md`, `docs/RECORD_AND_CAMPAIGN_REWORK.md`, `docs/CAMPAIGN_CONTINUITY.md`, `docs/IMAGE_GENERATION_RULES.md`를 읽는다. UI·Next.js 코드를 고칠 때는 설치된 Next.js의 관련 가이드도 읽는다.

이 스킬은 별도 에이전트 생성을 요구하지 않는다. 스킬 사용은 해당 지침을 읽고 작업에 적용하는 것이다. 더 최신의 사용자 지시와 프로젝트 후속 계약을 우선한다.

## 0. 범위 확정과 작업 기록

1. Git 상태와 기존 변경을 확인하고 사용자 작업을 보존한다. 외부 인증 정보나 사용자 실저장을 보고서에 복사하지 않는다.
2. 요청한 화 번호를 **실제 챕터 ID·제목·사건 원본 경로**에 매핑한다. 화면의 1화와 연표 5.1을 확인 없이 같은 것으로 취급하지 않는다. 기존 목록·생성기·관리자 데이터를 먼저 찾아 대응표를 만든다. 이 프로젝트의 원본은 `docs/romance-three-kingdoms/chapters/NNN.md`다. 로컬에 없으면 연결된 저장소 최신 트리에서 `chapters` 폴더를 먼저 찾는다.
3. 대상이 모호하거나 원본이 없으면 기존 자료로 확인 가능한 부분부터 조사한다. 대응을 확정할 수 없는 화는 질문을 남기고 임의의 사건을 만들어 대신하지 않는다.
4. 사용자 범위 요청이 명확하면 해당 범위의 개발 승인으로 본다. 예전 문서의 승인 범위보다 새로운 명시적 범위를 우선한다. 범위 밖의 수집·챕터 확장만을 위해 별도 확인한다.
5. [진행 기록 템플릿](references/chapter-ledger.md)을 사용해 `docs/development/<범위 식별자>.md`를 생성하거나 기존 기록을 이어 쓴다. 챕터별 상태·근거 경로·QA 점수 이력·이미지 목록·실행 명령·미해결 항목을 남긴다. 대화가 재개되면 이 기록과 실제 파일을 대조해 미완료 단계부터 이어간다.

## 챕터별 개발 루프

아래 1~8단계를 현재 화에 대해 끝낸 뒤에만 다음 화로 넘어간다.

### 1. 사건 파일 읽기와 사실 정규화

- 현재 화의 사건 파일을 끝까지 읽고 배경·단계별 전개·행위자·지역·세력·결과·선후관계·근거·미확인 사항을 추출한다. 이미 구현된 데이터와 비교해 중복 사건·중복 실행을 피한다.
- 기존 인물·지역·세력·사건 ID를 연결한다. 동명이인이나 사용자 확정 연결을 임의 변경하지 않는다. 월 미상은 미상으로 유지한다.
- 정사·연의·게임 창작을 분리한다. 출처 이견과 불확실성은 관리자 근거로 보존한다. 창작 속마음·대화·플레이어 개입을 사실 필드에 넣지 않는다.
- 원본만으로 중요한 전제를 확정할 수 없으면 수집 규칙과 승인 범위에 따라 필요한 자료만 보강한다. 접근 실패를 확인 성공으로 올려 쓰지 않는다.
- 산출물: 현재 스키마에 맞는 사실 데이터와 ID 대응, 진입 전제·역사 기본 경과·후속 영향 목록.

### 2. 실행 흐름 스킬 적용

- `three-kingdoms-flow`로 현재 화의 각 사건·장면을 설계한다. 상황 3~4문장, 1인칭 웹소설 독백, 행동과 속마음 형식을 따른다.
- A 원작 파괴/B 영웅 접촉·합류/C 생존의 선택 성격을 유지하되 실제 상태에서 성립하는 행동만 만든다. 기존 호환·특수 장면에서 세 선택을 강제하기 위해 불가능한 행동을 추가하지 않는다.
- 선택별 확정 조건, 필요 능력, 상대·비중, 성공/실패 결과, 상태 효과, 다음 노드·사건·엔딩을 정의한다. 확정 조건 미달과 확률 실패를 구별한다.
- 전투 통솔/무력, 일기토 무력, 논리 설득 지력, 임관 매력 등 실제 판정 규칙을 따른다. 기존 확률 엔진을 임의의 고정 최소치 방식으로 바꾸지 않는다.
- 행동→상대 반응→성패→상태 변화→다음 갈등을 연결한다. 결과 노드 없이 다음 선택으로 가는 경로도 결과 서술을 제공한다.
- 죽은 인물·패망 세력·변경된 역사 전제를 검사한다. 현재 화 말미의 소속·위치·생존·세계 표식과 다음 화 진입 계약을 정리한다.

### 3. 실제 데이터·게임·관리자 통합

- 설계표를 실제 실행 타입·검증 규칙과 대조해 구현한다. 사건 원본, 서사 원본, 생성기, 실행 목록이 재생성 후에도 일치해야 한다.
- `lib/event-flow-types.ts` 등 지원 스키마를 확인하고 노드·선택·조건·판정·효과·연결을 공통 사건 목록에 등록한다. 게임만 사용하는 숨은 별도 분기를 만들지 않는다.
- `/admin/events`의 조회·편집·저장과 `/admin/collection` 실행 플로우에서 같은 사건을 확인할 수 있게 한다. 새 필드가 필요하면 관리자 입력·검증도 함께 구현한다.
- 이전 기본본을 보존하고 필드별 호환 처리를 한다. 사용자 편집·명시적 삭제·진행 커서·기존 판정 결과를 보존한다. 공유 목록이나 로컬 편집본 전체를 기본본으로 덮어쓰지 않는다.
- 데이터 검증기와 필요한 타입·엔진 검증으로 끊긴 링크·고립 노드·효과 중복을 먼저 잡는다.

### 4. QA 스킬 적용과 필수 수정 루프

`three-kingdoms-qa`를 사용해 모든 선택 장면과 그 결과·후속 흐름을 평가한다. **논리·설정 / 문체 / 흐름 / 밸런스 / 도파민**의 다섯 점수, 근거, 결함, 리마스터를 기록한다. 챕터 평균만으로 개별 장면의 낮은 점수를 감추지 않는다.

**통과 기준은 다음을 모두 만족하는 것이다.**

1. 확인된 오류가 모두 수정되고 재검증됐다. 점수가 높아도 오류를 남기지 않는다. 취향 제안과 확인이 필요한 위험은 결함과 구분한다.
2. 각 선택 장면 및 챕터 전체의 종합 점수가 **7점 초과**다. **7.0점도 수정 대상**이다. 7점 이하이면 피드백 원인에 맞게 상황·선택·조건·결과·연결을 수정한다. 정당한 근거 없이 점수만 올리지 않는다.
3. 낮은 개별 항목은 원인을 검토하고 개선 또는 유지 근거를 남긴다. 사용자 기준은 종합 점수 7점 초과이며, 임의로 모든 항목 8점 같은 새 의무를 추가하지 않는다.
4. 현재 화에 필요한 실행 검증이 실제로 수행됐다. N/A·미실행을 높은 평균으로 덮지 않는다.

매 수정 후 영향받은 장면·선행/후행 경로를 다시 검수하고 이전 점수·수정 내용·재평가 근거를 남긴다. 성공·실패·C·조건 미달·비참가를 실제 엔진으로 확인한다. 미리보기 무추첨, 선택 확정 1회 판정, 재제출·저장 복원 시 결과 유지도 검증한다.

**오류를 고칠 수 없거나 필요한 도구·자료가 없으면 현재 화를 차단 상태로 남긴다.** 정해진 횟수만 반복한 뒤 자동 통과시키거나 다음 화로 건너뛰지 않는다. 해결 가능한 작업은 계속하고, 같은 원인으로 진전이 없으면 원인을 진단해 방법을 바꾸며 필요한 정보만 요청한다. 미해결 오류를 정상 동작으로 재정의하지 않는다.

### 5. QA 통과 후 분기 이미지 생성

- **4단계 통과 후** 이미지 제작을 시작한다. 생성 전에 최신 `docs/IMAGE_GENERATION_RULES.md`와 기존 기준 이미지를 읽고 실제 이미지를 열어 본다.
- `public/art/characters/`의 주인공·장수 기준, `public/title-screen.png`를 참조한다. 레트로 픽셀 아트·3등신, 주인공의 갈색 머리·회색 반소매 후드·청바지·갈색 배낭을 유지한다. 실제 기준 파일과 최신 규칙을 우선한다.
- 사건/노드/선택 ID별 이미지 계획을 만든다. **행동·진영·등장 상대·장소·시점·표정·화면 용도·참조 파일·저장 경로**를 적는다. A/B/C의 다른 행동을 같은 그림으로 대체하지 않는다. 선택 전 이미지가 성공·죽음·합류 등 미확정 결과를 스포일러하지 않게 한다.
- 이미 의미와 문맥이 정확히 맞는 자산은 재사용할 수 있다. 새 이미지가 필요한 분기는 이미지 생성 도구를 사용해 실제로 생성한다. 프롬프트·예정 경로만 작성하고 생성 완료라고 하지 않는다. 도구가 없으면 이미지 단계 미완료로 기록한다.
- 이미지 생성·편집은 제공된 이미지 생성 도구를 사용한다. 로컬 참조 이미지는 먼저 시각적으로 확인하고 경로로 참조한다. 유명 장수의 기준 이미지가 없으면 기준을 먼저 생성·저장해 이후 재사용한다.
- 생성 결과를 직접 열어 인물 외형·진영·실제 상대·행동 방향·감정을 검수한다. 오류가 있으면 수정·재생성한다. 파일명 존재나 자동 해시 검사로 의미 검수를 대신하지 않는다.
- `public/art/scenes/`, `public/art/choices/` 등에 저장하고 실제 `Artwork` 스키마·`lib/scene-art.ts`·`lib/choice-art.ts` 또는 기존 관리자 자산 연결 방식에 맞게 등록한다. 동일한 선택 ID라도 사건·노드 문맥으로 연결한다.
- 상황과 같거나 선택끼리 같은 그림이면 기존 규칙대로 선택 팝업 전체를 텍스트로 표시한다. 이 동작을 새 행동 이미지 제작의 대체로 남용하지 않는다.

### 6. 이미지 포함 최종 QA와 회귀 검증

- `three-kingdoms-qa`로 이미지 포함 장면을 다시 검수한다. 이미지와 문구가 다른 진영·인물·행동을 나타내거나 결과를 잘못 예고하면 반드시 수정한다. 문구·판정이 달라졌으면 점수와 분기 테스트도 다시 수행한다.
- PC·모바일·낮은 화면에서 상황 카드·선택 팝업·실제 결과·통합 기록을 확인한다. 주인공 얼굴/핵심 행동 잘림, 이미지 누락·이전 장면 잔류, 버튼 가림, 가로 넘침, 브라우저 오류를 검사한다.
- 관리자에서 새 사건·내부 노드·조건·판정·효과·연결·이미지를 조회하고 안전한 격리 데이터로 편집→저장→새로고침→게임 반영을 검증한다. 외부 공유 게시 권한이 없다면 격리된 저장으로 수행하고 검증 범위를 분명히 한다.
- 기존 테스트와 대상 변경의 의미 있는 엔진 경로를 실행한다. 최소한 다음 명령의 존재·대상 범위를 확인하고 적합한 검증을 실행한다:

```sh
npm run typecheck
npm test
npm run build
node scripts/validate-event-data.mjs
node scripts/validate-reference-data.mjs
git diff --check
```

현재 화를 지원하지 않는 기존 검증기를 통과시켰다고 현재 화가 검증됐다고 하지 않는다. 필요하면 현재 화의 검증 범위와 의미 있는 경로 테스트를 추가한다. 생성기가 있으면 재실행해 산출물이 안정적이고 편집·이미지 연결이 사라지지 않는지 확인한다.

이미 통과한 전체 검증은 새 수정·실패·미해결 우려가 없으면 불필요하게 반복하지 않는다. 화별 변경에는 관련 검증을 수행하고 요청 범위 마지막에는 전체 통합 검증을 완료한다. 빌드 산출물을 재사용할 때도 이후 변경이 결과를 무효화하지 않았는지 확인한다.

### 7. 챕터 완료 판정

현재 화의 완료 체크는 모두 충족해야 한다.

- 사건 원본과 실행 데이터의 대응·분류·근거·ID 연결이 확인됐다.
- A/B/C의 조건·판정·성공/실패·효과·후속 연결이 구현되고 주요 경로가 실제 실행됐다.
- 확인된 오류가 0개이며 장면별·챕터 전체 QA 종합 점수가 각각 7점 초과다.
- 필요한 상황·분기 이미지가 실제 생성/적절히 재사용돼 연결됐고 시각 검수됐다.
- 게임·관리자·이전 편집/저장 호환과 PC/모바일에서 필수 동작을 확인했다.
- 필요한 검증이 통과하고 현재 화에 필수인 미검증 사항이 남지 않았다.
- 다음 화의 진입 계약에 필요한 소속·위치·생존·세계 표식이 명시됐다.

하나라도 미충족이면 `진행 중` 또는 `차단`이다. 완료라는 표현과 다음 화 진행을 금한다. 기존 프로젝트의 무관한 실패가 발견돼도 조용히 무시하지 말고 영향·재현·원인을 분리해 기록한다.

### 8. 기록 후 다음 화 진행

화별 완료 기록에 실제 파일·사건/주요 노드 ID·관리자 직접 링크·QA 점수 이력·수정한 오류·이미지 경로·검증 근거·진입/종료 상태를 남긴다. 사용자에게 짧게 완료와 다음 화 착수를 알리고 **재승인 질문 없이** 다음 화 1단계로 넘어간다.

마지막 화 완료 후에는 범위 전체 연결을 검증한다. 앞 화의 분기별 종료 상태가 다음 화에 보존되는지, 독립 사건을 불필요한 필수 선행으로 만들지 않았는지, 역사 변경이 연속해서 반영되는지 확인한다. 결함이 발견되면 해당 화를 다시 진행 중으로 열고 수정·재검증한 뒤 완료 기록을 갱신한다.

## 최종 보고

요청 범위의 화별 완료 여부·QA 점수·수정 오류·주요 데이터와 이미지 경로·검증 결과를 간결하게 보고한다. 필수 항목이 미완료이면 정확한 차단 원인과 남은 작업을 적는다. 실제 수행하지 않은 이미지 생성·브라우저 검증·공유 게시·배포를 완료했다고 하지 않는다. 로컬 개발 완료와 운영 반영은 구분한다.
