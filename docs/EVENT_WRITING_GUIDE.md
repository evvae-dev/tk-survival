# 이벤트 수집·서사 작성 지침

## 화자와 적용 범위

모든 새 사건, 재수집 사건, 상황문, 선택지, 결과 로그에 적용한다. 화자는 삼국지 시대에 갑자기 떨어진 평범한 21세기 현대인이다. **1인칭 웹소설 독백체**로 당황·잔꾀·소소한 욕심을 드러낸다. 처음부터 군주·장군처럼 말하지 않는다. 실제 능력·소속·역할에 맞는 행동을 제시한다. 이 문체는 2026-10-16 후속 요청으로 확정한 최신 기준이며, 앞서 사용한 진지한 감각 묘사 중심 문체를 대체한다.

## 게임 이벤트 생성 규칙

1. **시점과 톤:** 21세기 현대인이 갑자기 떨어져 당황하는 1인칭 독백체를 쓴다. ‘당신은’으로 설명하는 2인칭 서술, 무거운 분위기, 긴 감각 묘사, 은유를 피한다. 인터넷 밈·캐주얼한 혼잣말을 상황에 맞게 섞는다. ‘나 지금 어떡하지?!’, ‘이게 왜 진짜야’ 같은 반응을 허용한다. 상황 설명은 반드시 **3~4문장**으로 짧게 쓴다. 밈을 억지로 여러 개 넣거나 동일한 농담을 반복하지 않는다.
2. **타이틀:** 반드시 **`[갑자기 분위기 황건적?!]`, `[여포가 왜 여기서 나와?]`**처럼 대괄호를 두르고, 가볍고 호기심을 끄는 웹소설 제목으로 쓴다. ‘진영과 전선’, ‘정세 변화’ 같은 추상적인 제목은 쓰지 않는다. 정확한 전투명·연월은 역사 개요와 메타데이터에 보존한다.
3. **선택지:** 반드시 **`[직관적인 행동] 현대인의 속마음`** 형식으로 쓴다. 예: `[냅다 도망친다] 영웅은 무슨, 일단 살고 보자!`. 대괄호 안에는 즉시 취할 행동, 뒤에는 1인칭 의도·잔꾀·당황을 적는다. 구현할 때 행동은 선택 제목, 속마음은 설명으로 나눠도 되지만 화면에서는 이 형식이 드러나야 한다. 수치가 필요하면 별도의 판정 안내로 표시한다. 성공을 미리 확정하지 않는다.
4. **세계와 독백의 구분:** 현대인의 비유·밈·‘나 지금 어떡하지?!’ 같은 혼잣말은 허용한다. 독자에게 직접 말을 걸거나 ‘어느 분기를 선택하시겠습니까?’, ‘기본 경과로 진행합니다’처럼 시스템을 해설하지 않는다. 정사·연의를 안다는 것과 모든 사건·인물을 즉시 알아보는 것은 구분한다.
5. **결과도 짧고 분명하게:** 결과를 제안할 때는 1인칭으로 1~2문장 안에 무슨 일이 벌어졌는지 쓴다. 성공·실패가 갈리면 각각 제시하고, 생존·포로·소속·승패·피해 등 실제 변화는 별도 결과 요약으로 명확히 알린다. 감상이나 농담만 쓰고 결과를 생략하지 않는다. 기존 판정·효과와 다른 결과를 지어내지 않는다.

## 앞으로의 수집·작성 절차

1. Codex가 해당 사건에 필요한 서브 절·전개·행위자·장소·개입 지점을 지정한다. 단순 탄생·사망, 평가·기타 창작물·관계없는 링크는 수집하지 않는다. 전투 결과로서의 사망은 보존한다.
2. Gemini CLI가 지정 페이지를 실제로 읽고 연월·정확도·지역·세력·관련 인물·내용·문헌명·사서기록·배경/전개/결과를 한국어로 수집한다. URL·원문을 출처명으로 대신하지 않는다. 조회 실패·이견·미확인 시기는 그대로 남긴다. 감각·창작 대화를 사실처럼 수집하지 않는다.
3. Codex가 장수·지역·세력 ID를 연결하고 소속별 행동·능력 판정·생존/포로·지배권·후속 사건 개방/취소를 설계한다. 한 연도의 여러 단계를 하나의 선택으로 뭉개지 않는다. 해결되지 않은 모호한 사실·동명이인은 사용자에게 질문한다.
4. 확정한 사실과 분기 위에 이 문서의 1인칭·3~4문장·대괄호 제목·행동과 속마음 형식으로 게임 문구를 작성한다. 정사·연의·가상역사를 출처 메타데이터로 구분한다. 창작 상황·대화는 `flow.nodes[].data.text`, 선택지는 `options[].title/description`에 넣는다. `summary`·`source.record`를 창작으로 덮어쓰지 않는다.
5. 성공·실패·비참가 결과까지 검수한다. 이미 죽은 인물이 지휘하거나 항복하지 않은 군대가 항복하는 등 세계 상태와 어긋나는 묘사를 금한다. 내부 그래프·사건 간 그래프·게임·공유본에서 같은 문구가 나오는지 확인한다.
6. 절 단위로 변경·이견·저장 위치를 보고하고 다음 절 진행 여부를 묻는다. 문체 수정 지시만으로 다음 절을 수집하지 않는다.

## 5.1 관리 위치

- 사실·이견: `data/collection/5-1-yellow-turban.json`
- 게임 문구 원본: `data/history/narrative-5-1.json`
- 분기 생성: `scripts/build-chapter-5-1.mjs`
- 문구 결합: `scripts/apply-chapter-narrative.mjs`
- 게임 실행·공유 게시 대상: `data/history/events.json`

재생성해도 문구 원본을 결합해 예전 문체로 돌아가지 않게 한다. 문구 정의가 없는 관리자 추가 노드·선택지를 만나면 게시 전에 중단하고 확인한다. 편집본을 조용히 기본 그래프로 교체하지 않는다.

2026-10-16에 5.1 사건 7개, 선택 장면 20개, 행동 선택지 56개, 결과 노드 59개에 적용했다. Firebase 공유 리비전은 `eccb1f96-fae9-4a6d-ad66-31985f3a7a92`이며 이전 리비전은 보존했다. 게시기는 `--narrative-only`일 때 현재 공유본의 문구만 바꾼다. `--dry-run`으로 쓰기 없이 적용 범위를 확인할 수 있다. 기존 진행 중인 게임의 노드 ID는 유지하며, 과거에 이미 저장된 기록 문장까지 소급해서 바꾸지는 않는다.

## 현재 데이터와 적용 범위

후속 요청으로 5.1 전체 문구에 최신 규칙을 적용했다. 사건 제목·20개 선택 장면·56개 선택지·59개 결과를 1인칭 캐주얼 문체로 작성했다. 기존 능력의 고정 기준 통과 방식은 [능력 확률 판정](ABILITY_CHECKS.md)으로 교체했으며, 체력·자금과 이에 따른 비용·피해는 사용하지 않는다. 실패 설명에 체력 감소나 자금 부족을 다시 넣지 않는다. 사료 원자료는 유지한다.

## 예시

**[갑자기 분위기 황건적?!]**

눈을 떠보니 누런 두건을 쓴 아저씨들이 횃불을 들고 ‘창천이 죽었다!’며 소리를 지른다. 스마트폰을 찾으려던 내 손에는 낡은 죽창 하나가 들려 있다. 반대편에서는 관군까지 달려오는데, 이게 왜 진짜야. 나 지금 어떡하지?!

- **[관군에 붙는다]** ‘저기요! 저 삥 뜯기는 민간인입니다!’ 일단 장비 좋은 쪽으로 붙자.
- **[황건적 코스프레]** ‘와아아! 황천당립!’ 누런 천만 묶으면 일단 같은 편처럼 보이겠지.
- **[냅다 도망친다]** 영웅이고 뭐고 일단 살고 봐야지! 사람 없는 뒷골목으로 뛴다.

## 선택 결과와 다음 장면의 인과 연결 (2026-10-18 추가)

현재 5.1의 수정·검수와 앞으로 승인받아 수집하는 모든 챕터에 적용한다. 다음 챕터의 수집을 지금 시작한다는 뜻은 아니다.

- 자료 수집 시 배경·전개·결과 외에 **직전 행동 → 상대의 반응 → 성패 → 실제 상태 변화 → 다음 상황의 원인**을 구분해 정리한다. 사료에 없는 협상 조건·약속·행위는 확정 사실로 만들지 말고 미확인 또는 게임 창작으로 표시한다.
- 선택지 설명은 행동 전의 의도다. ‘서로 칼 내려놓고 얘기하면 안 되나’ 같은 속마음을 선택 후 결과로 재사용하지 않는다. 협상이 성공했다면 ‘내가 내건 조건을 한충이 받아들여 협상이 성사됐다’처럼 **어떤 행동이 어떤 반응을 얻었는지** 먼저 확정해서 쓴다. 실패한 경우도 거절·공격 저지 등 실제 실패를 먼저 보여준다.
- 판정 안내의 성공 확률이나 ‘성공’ 색상은 서사의 결과 문장을 대신하지 못한다. 플레이어가 안내를 접거나 다음 상황만 읽어도 성패와 바뀐 상태를 알 수 있어야 한다. 판정 직후 결과 노드 없이 다음 선택으로 연결되는 모든 경로에도 별도의 결과 서술을 준비한다. 판정 데이터의 `successNarrative`·`failureNarrative`에 1인칭 과거형 1~2문장을 두고 기록에 출력한다.
- 다음 장면은 직전 결과를 짧게 받아 시작한다. 협상 성공 → 한충의 무장 해제·항복 → 진힐 측의 처형 시도처럼 원인과 새 갈등을 연결한다. **협상·항복 수락은 처형 중단이나 신변 보장 성공과 별개**다. 후속 선택에서 결정될 사람의 생존·포로 처우를 앞 장면에서 이미 해결했다고 쓰지 않는다.
- 합류·이동·전투·설득·구출·항복 등 모든 경로를 성공·실패·비참가별로 끝까지 읽는다. ‘왜 갑자기 항복했지?’, ‘누가 누구를 이겼지?’, ‘왜 이 장소에 있지?’라는 질문이 남으면 연결 문장이 빠진 것으로 본다. 공통 후속 장면은 앞선 성공/실패가 달라도 성립하는 문장으로 쓰고, 특정 결과를 단정해야 하면 경로별 결과 문장으로 나눈다.
- 게임 실행문과 문구 원본을 함께 수정하고, 재적용 후 ID·연결·조건·수치·효과·생존 판정이 바뀌지 않았는지 확인한다. 저장 기록과 실제 화면에서도 결과가 숨겨지거나 의도만 남지 않는지 검사한다. 알려진 구문만 대상으로 기존 저장의 표시를 보완하며, 관리자가 작성한 다른 문구는 덮어쓰지 않는다.

한충 협상의 연결 예시:

> 결과: 내가 내건 조건을 한충이 받아들여 협상이 성사됐다. 한충과 병사들이 무기를 내려놓았고, 나는 관군에 항복한 사람들을 살려 달라고 전했다.
>
> 다음 상황: 내가 내건 조건을 한충이 받아들여 협상이 성사됐다. 한충과 병사들이 무기를 내려놓자 이제 싸움이 끝난 줄 알았다. 그런데 진힐 쪽 병사가 포승줄에 묶인 한충 앞에서 칼을 뽑는다. 아니, 항복을 받아놓고 이제 와서 죽이겠다고?!

## 관리자 등록·편집 보장 (2026-10-19 추가)

사용자가 요청한 상시 작업 규칙이다. 앞으로 추가하는 모든 사건·가상 시나리오·분기에 적용한다.

- **등록:** 새 사건은 고유 사건 ID로 공통 사건 목록에 등록하고, 기존 사건의 새 분기는 해당 사건의 `flow`에 노드·선택지·조건·판정·결과·효과·연결로 등록한다. 게임 실행과 `/admin/events`, `/admin/collection`이 같은 데이터를 사용하도록 한다. 게임에서만 실행되는 별도 분기를 만들어 관리자 편집에서 빠뜨리지 않는다.
- **편집:** 추가한 내용은 관리자에서 조회·검색·선택하고 문구·조건·판정·효과·연결을 수정·저장할 수 있어야 한다. 새 데이터 형식이나 효과를 도입하면 관리자 편집 필드와 검증도 함께 지원한다. 생성기와 문구 원본에도 추가하여 재생성 시 새 내용이 사라지지 않게 한다.
- **기존 목록 호환:** 이전 공유 목록이나 로컬 편집본을 불러왔을 때 새 항목이 누락되거나 자동 삭제 처리되지 않는지 확인한다. 기존 문구·노드·선택·효과·연결·배치를 보존하며 필요한 새 항목을 추가한다. 관리자가 명시적으로 삭제한 항목은 임의로 되살리지 않는다.
- **완료 기준:** 관리자 목록과 실행 플로우 표시, 사건 제목·ID 검색과 직접 링크 열기, 추가한 노드·조건·효과·연결의 편집·저장, 새로고침 후 복원, 이후 게임 실행에 수정 내용이 반영되는지 확인한다. 기본 목록뿐 아니라 이전 공유 목록·편집본에서도 새 항목이 표시되는지 검증한다.
- **완료 보고:** 추가한 사건명·사건 ID·주요 내부 노드 ID와 `/admin/events?event=<사건 ID>` 직접 링크를 안내한다. 관리자에 등록되지 않았거나 편집·저장을 검증하지 못한 상태를 완료로 보고하지 않는다.
